# ER-to-Relational Mapping — Stationary Shop

ER diagram: `database/er_diagram/er_diagram.png` (also `.svg`, `.pdf`; editable source `er_diagram.dot`,
generated by `make_er.py`). The tables below are exactly those created by `database/stationary_shop.sql`.
The script `database/tests/er_matches_schema.py` compares the diagram with the live database (tables, columns,
primary, foreign and unique keys) and reports any difference.

## 1. Mapping rules applied
| ER construct | Relational result |
|---|---|
| Strong entity | One table; entity key becomes the primary key (identity column) |
| 1 : N relationship | The primary key of the "1" side becomes a foreign key in the "N" side table (Category→Product, Supplier→Product, Supplier→Purchase Order, Customer→Order, Employee→Order, Product→Stock Log) |
| M : N relationship with attributes | A separate table holding both foreign keys plus the relationship attributes. *Contains* (Order–Product) → `order_items`; *Includes* (Purchase Order–Product) → `purchase_order_items`. A surrogate key (`item_id`, `po_item_id`) is the primary key |
| 1 : 1 relationship | *Paid by* (Order–Payment): the foreign key `payments.order_id` is also `UNIQUE`, so an order has at most one (full) payment; the Order side is partial because a Pending order has no payment yet |
| Partial participation of the N side | Foreign key is nullable (`orders.customer_id` NULL = walk-in customer; `products.supplier_id`) |
| Total participation | Foreign key is `NOT NULL` |
| Derived attribute | `order_items.line_total` is a stored generated column (`quantity * unit_price`); the order total comes from `get_order_total()` |

## 3. Relational schema (compact)
```
categories(category_id PK, category_name UK, description)
suppliers(supplier_id PK, supplier_name, contact_person, phone, email UK, city)
products(product_id PK, product_name, brand, category_id FK, supplier_id FK, cost_price, price,
         stock_qty, reorder_level, is_active, created_at)
customers(customer_id PK, customer_name, phone UK, email UK, city, loyalty_points, joined_on)
employees(emp_id PK, emp_name, role, phone, salary, hired_on)
orders(order_id PK, customer_id FK?, emp_id FK, order_date, discount_percent, status, request_key UK?)
order_items(item_id PK, order_id FK, product_id FK, quantity, unit_price, line_total)
payments(payment_id PK, order_id FK UK, amount, method, paid_at)
purchase_orders(po_id PK, supplier_id FK, po_date, status)
purchase_order_items(po_item_id PK, po_id FK, product_id FK, quantity, unit_cost)
stock_log(log_id PK, product_id FK, change_qty, reason, logged_at)
```

## 4. Normalisation note
All tables are in 3NF: every non-key attribute depends on the key, the whole key and nothing but the key.
`unit_price` in `order_items` is deliberately stored (price at the time of sale) so that later price changes do
not alter old bills; this is a design decision, not a redundancy.
